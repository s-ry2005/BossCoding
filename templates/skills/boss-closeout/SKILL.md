# BossCoding 完整收尾

先完整阅读项目根目录的 `AGENTS.md`，再用项目已有命令和真实环境核实状态。不要从旧文档、CI 绿灯或“部署成功”字样推断用户已经拿到可用结果。

## 五个不可混用的状态

按事实逐项标记，不能核实就写 `pending`：

| 状态 | 成立条件 |
|---|---|
| 已合并 | 改动已进入稳定分支 |
| 已部署 | 目标环境已收到该版本，且部署版本或提交可对应 |
| 线上已验证 | 在真实线上入口完成核心用户路径检查 |
| 知识已收尾 | 代码、运行态、文档、规则、获准维护的记忆和工作区已对齐，遗留项已明示 |
| 已清理 | 老板看完完整报告后明确确认，且指定的分支、工作区和临时资源已实际回收并复查 |

没有部署目标的本地工具，将“已部署”和“线上已验证”标为 `not-applicable`，但仍要核实本地交付物和知识收尾。合并不自动推出部署；部署不自动推出线上已验证；知识已收尾不自动推出已清理。

## 1. 部署与真实线上验证

1. 先核对稳定分支、远端、部署触发者、目标环境和版本标识。部署、花钱、权限、密钥或对外发布属于项目红线时，先说明影响并等待老板确认。
2. 部署完成后，直接打开真实地址或调用真实接口，检查至少一条核心用户路径和本次改动涉及的关键结果；网页要看实际页面，不用构建日志替代。
3. 把检查的入口、时间、版本或提交、路径与结果记入项目现有的交付文档或决策档案。无法取得真实入口、凭据或环境时，写明阻碍和下一步，状态保持 `pending`。
4. 线上验证失败时，先修复或按保留历史的方式撤销；不以“CI 已通过”“接口可访问”或“部署命令退出 0”宣称成功。

## 2. 知识收尾与复盘

1. 调用 `neat-freak`，按其完整或轻量路径核对代码、运行态、文档、规则、获准维护的记忆和工作区。它不可用时，执行同等六面审计，并在报告中标为“neat-freak 等价人工收尾”。
2. 以当前代码和真实运行态为准，修正受本次改动影响且已验证过期的 README、运行/部署说明、规则和索引；重大长期裁决只追加到 `docs/decisions/`，不改写历史。
3. 复盘只记录真实发生、未来可复用的经验；没有新经验可以明确写“无”。不把未验证的推测写成规则或记忆。
4. 输出完整收尾报告：用户得到的结果、五个状态、验证证据、已同步的知识面、`pending`/`out-of-scope` 项和候选清理对象。此时保留现场供复核。

## 3. 确认后才清理

1. 只读列出可回收对象：已合并且干净的任务工作区、对应分支、临时数据库或本次生成的临时产物；逐项说明影响和恢复方式。
2. 不把任务开始时的“做完后清理”当成确认。必须在完整收尾报告后，等待老板明确说可以清理。
3. 确认后由 AI 执行清理并重新审计；禁止删除未合并、未提交或无法确认内容已进入稳定版本的对象。
4. 补充报告实际删除项、复查结果和仍存在的警告。未获确认时，状态停在“知识已收尾”，不要删除任何内容。
